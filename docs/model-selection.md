# Model Selection

Covers AC-10: at least two candidate LLMs evaluated on the custom eval set, with
metrics and a selection rationale.

Measured results are in `reports/model_comparison.md` and
`reports/model_comparison.json`, regenerated by `catalog-rag compare`.

---

## 1. The constraint

Google Gemini is the only approved provider (Open-Source & No-Docker Rule), so
the comparison is between Gemini models, not across vendors. That is a narrower
question than "which LLM", but it is the decision that actually had to be made
here: **which Gemini model generates the answer**.

Note what is *not* being compared. Embeddings and reranking are local
Sentence-Transformers models, chosen separately in
[embedding-selection.md](embedding-selection.md). Those choices affect retrieval
quality; this document is only about the generator.

## 2. Candidates

Discovered by listing what the API key can actually reach, rather than assuming
from documentation:

```bash
catalog-rag doctor      # reports which configured models are reachable and in quota
```

| Model | Class | Why considered |
|---|---|---|
| `gemini-3.5-flash` | Current-generation, thinking | Highest quality of the flash tier |
| `gemini-3.5-flash-lite` | Current-generation, lightweight | Cheapest and fastest; the cost/latency floor |
| `gemini-3-flash-preview` | Current-generation | Alternative flash variant |

`gemini-2.5-*` models are not provisioned on this API project, so the two
carried into the committed comparison are set in
`config/config.yaml` under `eval.comparison_models`.

## 3. Method

The comparison isolates the generator:

- **Identical retrieval.** Same index, same BM25 and vector arms, same RRF
  parameters, same reranker, same final top-K. Both models see the *same
  retrieved clauses* for every question.
- **Identical prompt.** Same system prompt and same structured-output schema.
- **Identical dataset.** The same committed 20-question golden set.
- **Temperature 0** for both, so runs are reproducible.

Only the generator changes, so any difference in the scores is attributable to
the model rather than to retrieval noise. `reports/model_comparison.json`
records this explicitly in its `note` field, and
`test_ac10_comparison_is_a_fair_test` asserts it.

## 4. What is measured

**LLM-judged (RAGAS):** context precision, context recall, faithfulness, answer
relevancy.

Note that **context precision and context recall are properties of retrieval,
not of the generator**, and retrieval is held constant. They should therefore be
near-identical between the two models. If they diverge meaningfully, something
in the comparison is not actually controlled, and the run should be treated as
suspect rather than as a finding. They are reported precisely because they act
as a control.

The metrics that genuinely discriminate between generators are **faithfulness**
and **answer relevancy**.

**Deterministic (no judge, exactly reproducible):**

| Metric | Why it matters here |
|---|---|
| `citation_rate` | Does the model reliably produce clause-level citations? (AC-02) |
| `abstention_accuracy` | Does it correctly refuse the out-of-corpus questions? (AC-05) |
| `false_abstentions` | Does it refuse questions it should have answered? |
| `mean_latency_seconds` | Wall-clock cost per query |
| `pipeline_errors` | Must be 0, or the run is not comparable at all |

## 5. Selection criteria, in priority order

Ranked deliberately, because the models will not win on every axis:

1. **Faithfulness.** The business case argues that a confidently wrong compliance
   answer is worse than no answer. This dominates.
2. **Citation rate and abstention accuracy.** The guardrails catch failures here,
   but a model that needs the guardrails constantly is doing worse work than one
   that does not.
3. **False abstentions.** Excessive caution has a real cost — an assistant that
   refuses half its questions is not useful.
4. **Answer relevancy.** Quality of the answer given correct grounding.
5. **Latency and cost.** A real consideration, but the last tiebreaker rather
   than a leading criterion.

## 6. Operational finding: quota is a selection criterion

This is worth recording because it changed the decision, and it is not visible
in the metrics table.

During evaluation, `gemini-3.5-flash` **exhausted its quota partway through the
golden set**. Questions G01–G11 completed normally; G12 onward returned
`429 RESOURCE_EXHAUSTED`. A sustained retest at 8-second spacing returned 8/8
failures, confirming a daily cap rather than a per-minute rate limit — while
other Gemini models on the same key remained reachable, showing that quota is
tracked per model.

Two things came out of this:

**A code fix.** The pipeline had been recording provider failures as
abstentions. The corrupted run reported ten "false abstentions" that were
actually API errors, which made a broken run look like a cautiously behaving
one. `AnswerStatus.ERROR` is now distinct from `AnswerStatus.ABSTAINED`, errored
questions are excluded from the metrics and counted separately as
`pipeline_errors`, and the harness raises rather than writing `nan` into a
report. See [failure-taxonomy.md](failure-taxonomy.md) §6.

**A pre-flight check.** `catalog-rag doctor` verifies quota before a long run,
and `run_evaluation()` fails fast rather than producing a report full of
failures forty minutes later.

The engineering lesson generalises beyond this project: **a model you cannot get
enough quota on is not a candidate**, however good its outputs are. Availability
belongs in the selection criteria alongside quality.

## 7. Measured results

Both models answered the same 20-question golden set with identical retrieval
configuration, prompts and reranking. Source: `reports/model_comparison.json`. Both models were judged by the same model (`gemini-3.5-flash-lite`) in the same run.

| Metric | `gemini-3.5-flash` | `gemini-3.5-flash-lite` | Winner |
|---|---|---|---|
| **faithfulness** | 0.8309 | **1.0** | **lite** |
| **answer relevancy** | 0.8099 | **0.8542** | **lite** |
| context precision | **0.6922** | 0.6856 | flash (marginal) |
| context recall | **0.9265** | 0.9118 | flash (marginal) |
| retrieval recall | 0.8966 | **0.9655** | lite |
| clauses found | 26/29 | **28/29** | lite |
| **false abstentions** | 2 | **0** | **lite** |
| citation rate | 1.0 (15/15) | 1.0 (17/17) | tie |
| abstention accuracy | 1.0 (3/3) | 1.0 (3/3) | tie |
| mean latency | 11.56s | **8.95s** | lite |
| pipeline errors | 0 | 0 | tie |

## 8. Selection: `gemini-3.5-flash-lite`

**Rationale, against the criteria in §5:**

1. **Faithfulness (top criterion): lite wins decisively**, 1.0 vs 0.831. The
   business case argues a confidently wrong compliance answer is the worst
   outcome, so this is the metric that matters most, and the gap is large.

2. **Citations and abstention: tied.** Both achieved a 1.0 citation rate and
   refused all three out-of-corpus questions correctly.

3. **False abstentions: lite wins.** `gemini-3.5-flash` refused two questions
   the corpus answers (G13 and G15); flash-lite refused none. Two wrongly
   refused questions out of seventeen is a real usability cost.

4. **Answer relevancy: lite wins**, 0.8542 vs 0.8099.

5. **Latency and cost: lite wins.** 8.95s against 11.56s, and materially
   cheaper, because `gemini-3.5-flash` is a *thinking* model whose internal
   reasoning tokens are billed as output.

`gemini-3.5-flash` won only context precision and context recall, both by small
margins — and those measure *retrieval*, which was held constant, so they are
better read as run-to-run noise than as a property of the model (see the caveat
below).

**The lighter, cheaper, faster model was also the more faithful one.** That is
not the result we expected, and it is the reason the comparison was worth
running rather than assuming the larger model would win.

Configured as `llm.primary_model` in `config/config.yaml`. Changing it is a
one-line edit; nothing in the codebase hard-codes a model name.

### Caveat on the controlled comparison

Retrieval was intended to be identical across models, and the retrieval
*configuration* was. But `retrieval_recall` differed (0.8966 vs 0.9655), which
it should not if retrieval were truly identical.

The cause is that **query transformation is itself an LLM call**. Even at
temperature 0 the rewritten query varies slightly between runs, which changes
what is retrieved. So the comparison isolates the generator's *prompt handling*
but not perfectly its retrieval inputs.

This is a genuine limitation of the experiment and is reported rather than
smoothed over. It also means the context precision and recall differences should
not be attributed to the models.

## 9. Note on the metric that nearly went missing

`ResponseRelevancy` initially returned `nan` for every sample. Three separate
causes were found: our embeddings class exposed a `.model` attribute that RAGAS
expected to be a model-name string; RAGAS requested multiple candidates in a
single call, which these Gemini models reject; and the API account's prepaid
credit was exhausted, which surfaced as a timeout rather than an error.

All three are fixed, and the metric is now computed for both models. The harness
raises rather than writing `nan`, so a metric that cannot be computed is visibly
absent instead of appearing as a fabricated measurement.
